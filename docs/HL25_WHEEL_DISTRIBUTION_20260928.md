# HL25 wheel probability and pacing audit — 2026-09-28

> Runtime default was changed in the [0.05% production-operations follow-up](HL25_WHEEL_005_FORECAST_20260928.md): pacing is now opt-in (`Hl25:WheelTargetEligibleSpins > 0`), while the default is absolute weighted random. The 3,000-spin results below apply only when that target is explicitly configured.

## Finding and evidence

The original `SpinAsync` called `PickSlotByWinRate`, which rolled uniformly over `Sum(WinRate)`. With the requested six rates summing to 100, that algorithm is mathematically correct: each gift has 1.67% probability **per eligible spin**. It silently normalized an invalid total, however, and both public/Admin config readers used unordered `FirstOrDefault` despite no unique WheelConfig constraint. Neither defect can be proven to have occurred in production without the production DB/history.

At 1,600 independent eligible spins, one 1.67% gift has mean 26.72, standard deviation 5.126, and `P(X >= 50) = 0.000031096` (about 1 in 32,158). The probability **any of five** reaches 50 is at most 0.000155481 (union bound, about 1 in 6,432). If 1,600 includes spins by participants who had already won, the relevant eligible denominator is smaller and the pure-random tail is even lower. This makes 50 at 1,600 unusual, not mathematically impossible. In any case, pure random cannot guarantee that gifts stay available until near spin 3,000.

Only the local `GenoraMultiTenancy` database was reachable with the workspace connection settings. Read-only audit: one active config, six current slots (`1.6700 × 5 + 91.6500 = 100.0000`), one SpinLog (NotWon), zero allocated gifts. Its five gifts have quantities 1,000/500/500/500/500 and current aggregate `TotalQuantity - RemainingQuantity = 41`, while no SpinLog has a GiftId. Admin gift updates can directly change RemainingQuantity, so stock delta is not a reliable proxy for wins. These are **not** the reported production data (1,600 spins, 50 per gift). `docs/HL25_WHEEL_AUDIT_20260928.sql` is read-only and returns config/slot IDs and rates, eligible/total/prior-winner spins, per-gift allocation/stock delta/observed rate, 50th-award ordinal, duplicate winners, and slot/reward-status breakdown. Historical WinRate/config values were not snapshotted in SpinLog, so current slot values cannot prove what rate an old spin used.

## Flow and changes

`POST /api/mini-app/hl25/wheel/spin` → `MiniAppHl25Service.SpinAsync` → active config and its slots → participant and remaining turns → eligible ordinal → paced slot → live gift/stock and prior-award checks → decrement one turn/one gift, create one SpinLog → ABP transactional commit. The one-gift rule now checks both `TotalGiftsWon` and prior GiftId SpinLogs, so a drifted participant counter does not create a second winner. A SQL Server transaction-owned application lock is taken **before** reading participant/stock and remains held through commit. The same lock works across Web processes. Local SQL lock probe: first acquisition 0, concurrent acquisition -1 (timeout), acquisition after first commit 0. ABP `ConcurrencyStamp` remains on participant/gift aggregates. A logging failure after commit is ignored so it cannot return an error after issuing a gift.

The new schedule uses absolute WinRate. Validation requires exactly 100.0000%, one no-gift slot, one slot per GiftId, and decimal values representable by `decimal(9,4)`. Multiple active configs or multiple inactive configs fail clearly; one active config is used consistently by Admin and MiniApp. Admin JS accepts `1,67` or `1.67`, checks exact total and unique gift assignment before save; backend still validates. Runtime emits a structured, PII-free committed-spin log with ConfigId, slot count/sum, eligible ordinal, selected slot/rate, gift and SpinLog IDs. The public API does not expose WinRate.

For the first `Hl25:WheelTargetEligibleSpins` (default **3,000**) eligible spins, each gift receives `min(TotalQuantity, round(targetSpins × WinRate / 100))` scheduled winning positions, one randomly placed in each equal-sized interval. Positions are unique across gifts. The positions derive deterministically from the wheel configuration ID (not returned by the public API) and slot IDs and are identical across Web nodes; edits to slots/rates/quantities produce a new cached schedule. A participant who already won lands on the no-gift slot and does not increment the eligible ordinal. A scheduled gift unavailable due to stock/status/prior allocations also lands on no-gift. After the target spin count, remaining inventory follows validated weighted random. `CountPriorAwards` and live stock cap allocations; the existing maximum of one gift per participant remains.

For the requested five 1.67% gifts with 50 pieces each, each gift is scheduled once per 60-eligible-spin interval: at 1,600 eligible spins it has 26 or 27 scheduled wins; at 3,000 it has 50, subject to remaining stock and prior awards. Existing early allocations cannot be reversed. Editing a live wheel can change future winning positions; do so only as a deliberate campaign change. Admin can also alter stock outside the spin lock; ABP optimistic concurrency protects conflicting aggregate updates, but operational reconciliation remains important.

## Simulation and verification

Simulation uses the same `Hl25WheelDistribution` code called by `SpinAsync`, without stock decrement. One seeded 100,000-trial pure-weighted run: gifts **1,672 / 1,751 / 1,658 / 1,697 / 1,648**, no-gift **91,574**. One 100,000-trial paced run: gifts **1,703 / 1,650 / 1,679 / 1,661 / 1,720**, no-gift **91,587**. The paced long run uses weighted random after the first 3,000 turns; individual samples vary.

Across 500 pure-random batches × 3,000 spins (2,500 gift observations): at 1,600 mean **26.665**, min/max **11/44**, SD **5.084**; at 3,000 mean **50.140**, min/max **27/77**, SD **7.032**. Across 200 paced batches × 3,000 spins (1,000 gift observations): at 1,600 mean about **26.67**, min/max **26/27**, SD about **0.47**; at 3,000 mean/min/max **50/50/50**, SD **0**. Tests assert these boundaries and exact inventory-safe schedule counts. The runtime additionally checks status/stock and prior awards.

Domain simulation 5/5, HL25 Application 45/45, HL25 Web 42/42, Admin JS regressions 3/3 passed. EF Core project and Web Release build passed (0 errors); Web Debug build initially failed copying assets into a locked output folder, so Release was used. SQL audit script executed read-only against local host and returned seven expected result sets. No EF model change or migration, no DB write or production deployment, and no public API/DTO shape change.

## Limits and rollout checks

- Run the read-only audit SQL on the **actual** production tenant database before assigning the historical 1,600/50 event to data drift, config ambiguity, manual stock edits, duplicate requests, or chance. Current local data cannot establish that cause. Compare `GlobalSpinAt50thAward` and `EligibleSpinCount`, then inspect the structured logs around the event if retained.
- The Mini App frontend caller is in a separate repository; this repo has one POST spin endpoint and the load-test journey deliberately calls it twice. No client idempotency key exists. Serialized requests cannot spend the **same** remaining turn twice, but two duplicate requests when the participant has two turns can still consume both. Exactly-once per UI action requires a client request ID and persisted uniqueness, coordinated with that frontend.
- The transaction lock serializes spins per wheel and can reduce throughput at bursts. A 15-second lock timeout returns `Hl25:WheelBusy` before consuming a turn. It was probed on SQL Server, but no authenticated end-to-end production load test was run; measure queue time and latency before deploying at high traffic. The eligibility query reconstructs prior-winner state from historical SpinLogs and grows with campaign size.
- Current `WinRate` and `TotalQuantity` on local DB differ from the requested production inventory. If production has gift status/quantity changes or rates edited mid-campaign, the historical schedule may not land every remaining gift exactly by spin 3,000. Inventory never exceeds available stock or the target count during the paced phase; historical allocations are not repaired by code deployment.
