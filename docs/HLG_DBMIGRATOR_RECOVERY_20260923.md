# HLG DbMigrator recovery — 2026-09-23

`dotnet run -- --migrate-database` originally failed at tenant `Test1` in migration `20260919112304_AddHlgDesignContent`. `Test1` had **zero HLG objects** but `__EFMigrationsHistory` already listed the five HLG baseline migrations. The guard in `AddHlgDesignContent` correctly refused to add columns to nonexistent tables. This is the same schema/history drift previously repaired on host `GenoraMultiTenancy`; it is not caused by the unrelated C# build warnings.

Read-only inventory before repair showed `Test2` had 13 baseline HLG tables/five history rows and only lacked `AddHlgDesignContent`. The other six tenant databases and host already had six HLG migration rows. The host-level `Hlg.Management` feature was set only for `Hoa Linh Miền Nam`, but the shared EF migration set creates HLG tables in every tenant database regardless of feature activation; suppressing the guard for feature-disabled tenants would leave a false schema state.

`docs/HLG_TEST1_SCHEMA_REPAIR_20260923.sql` is the host repair adapted to the exact `Test1` database. It defaults to dry-run and refuses any other database, any HLG object, any unexpected HLG history row, or a second run. Dry-run found the exact five baseline rows. Its apply branch ran once; the five deleted history rows were saved in `Test1.dbo.HlgMigrationHistoryRepair_20260923`. `dotnet ef database update --no-build --connection <Test1 Default connection>` then replayed five baseline migrations and applied design-content. The same explicit-connection command applied only design-content to `Test2`, with no history reset.

The schema migrator now pings an existing target database first. It connects to `master` only when SQL Server explicitly reports missing database (4060/911), quotes a new database name via `QUOTENAME`, and no longer attaches a full connection string to `TenantDatabaseUnreachable` error data. The existing-database path was exercised by the full staging run; creating a brand-new database was not tested in this task.

The in-sandbox run hit a separate machine TLS error while connecting to `AmiHairSalon` (`The instance of SQL Server you attempted to connect to requires encryption but this machine does not support it`). Read-only SQL and explicit EF updates worked. Running the same built DbMigrator outside the sandbox completed all databases and seeding with exit code 0; this confirms the TLS failure was specific to the sandbox execution environment, not the HLG schema repair.

Post-run read-only verification across **nine distinct databases** (`GenoraMultiTenancy`, `AmiHairSalon`, `BlueDiamondGolfLinks`, `DuocPhamHoaLinh`, `HoaLinhMienNam`, `LagunaGolfLangCo`, `MontgomerieLinks`, `Test1`, `Test2`) found **17 HLG tables, six HLG migration history rows, and the design-content migration recorded in each**. `Test1` and host each have five backup history rows. DbMigrator build succeeded with 0 errors (existing warnings remain). The final full command printed `Completed database migrations.` and exited 0.

No full database backup was created by this task; only the five `Test1` HLG history rows were copied into a backup table. Existing log-file changes in the workspace were left untouched. The separate HLG Admin menu problem still requires publishing the current Web package to both IIS staging hosts; see [staging recovery](HLG_STAGING_RECOVERY_20260923.md).
